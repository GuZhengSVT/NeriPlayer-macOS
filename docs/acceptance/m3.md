## 测试基础设施问题（既有，非本里程碑引入）

`PlaybackStateStore` 把引擎状态折叠进内存态，靠的是一个**非结构化 `Task` 消费 `AsyncStream`**。
该任务在调度不利时可能长时间不被唤醒，表现为一批 store/UI 用例等快照超时（8~20s）。
**这是 M1 引入的既有问题，不是 M3 造成的**；M3 只是让它在跑的用例更多时更容易被撞上。

实测结论：

- 触发概率并不低：连续跑全量，命中率约 **1/2 ~ 1/4 轮**（含**无外部负载**的干净运行）；
  早期观察到的「只有加压才复现」偏乐观了。
- 失败现场固定为：store 当前快照与订阅者最后收到的快照**完全一致**且都停在旧值
  （典型是 `load()` 里那次同步 publish 的结果），说明不是「测试等错东西」，
  而是折叠任务没被调度。
- 已排除：任务优先级（改 `.userInitiated` 后仍复现）、真实音频输出（静音后仍复现）。
- 埋点取证遇到 heisenbug：加上「每次状态变化写一行文件」的埋点后连跑 4 轮全量均通过 ——
  埋点的 I/O 本身改变了时序。clean 代码下用 `log stream` 抓不到（`info` 级不落盘）。
- 命中过的用例：`PlaybackEntryUITests.testStatusTextFollowsEngineSnapshotChanges` /
  `testStatusTextShowsStoppedAfterStop`、`PlaybackStateStoreTests.testFakeRepeatAllEOFAdvances` /
  `testFakeSequentialEOFAtEndStops` / `testEnqueueKeepsCurrentTrack` /
  `testRepeatOneReplaysCurrentTrackAfterEOF`。

本次已消除其中属于**测试自身**的部分（3 处，见提交 7663a40 与 ab66c3b）：

- 在有损流（`bufferingNewest(1)`）上断言「某条历史文案必须出现过」——改为断言
  「订阅者已追平 store 当前快照」这一必然收敛的不变式；
- 用 `contains` 匹配重复文案导致等待提前假通过；
- 重载用例拿「非空闲」当加载完成信号，而引擎在上一首时就已非空闲。

剩余部分属**产品侧调度问题**，建议另开任务处理。候选方向（按风险从低到高）：

1. 给状态折叠一个不依赖协作线程池的执行体（例如引擎事件线程上的同步回调），
   代价是 `PlayerEngine` 协议要加一个观察者注册口，测试替身需同步跟进；
2. 让 `publish()` / `snapshot` 在读路径上同步折叠引擎真值。风险高：EOF 自动推进依赖
   `playbackArmed` 闩锁的「先离开空闲、再回到空闲」顺序，在读路径上折叠会打乱该顺序，
   必须把推进逻辑一并搬过来，否则会破坏 M1 的自动续播语义 —— 不建议在没有专项测试前动。
